# Docker Compose

Docker Compose is the fastest way to run `auth-server` locally exactly the way it runs in production, together with its Redis and MongoDB/PostgreSQL dependencies, without installing any of them on your host. It's also reasonable for a small, real, single-host deployment. [Kubernetes (Helm)](/docs/auth/auth-server/deployment/helm) is the better choice once you need more than one replica or don't want to babysit the host yourself.

A pre-built image is published to [GitHub](https://github.com/orgs/rapidrest/packages) for every tagged release, as both `ghcr.io/rapidrest/auth-server:latest` and the release's own version tag (the current release is `1.0.0`). The Compose setup below doesn't pull either of these. It builds the image from your own checked-out `Dockerfile`.

## Architecture

Compose builds the image from the repository's `Dockerfile` and starts three containers on one network: `server` (the `auth-server` API), `redis` (cache, events, and log streaming), and either `mongo` or `postgres` (the primary datastore, depending on the compose file chosen).

```text
      -----------------------------------------------------
     |                  compose network                     |
     |                                                       |
     |   ------------      ------------      --------------- |
     |  |   server   |<-->|   redis    |    | mongo/postgres| |
     |  | (built from|    |  (cache,   |    |  (primary     | |
     |  | Dockerfile)|    |  events,   |    |   datastore)  | |
     |   ------------      |  logs)    |     --------------- |
     |        |             ------------                     |
      -----------------------------------------------------
              |
     host:3000 (API)        host:9229 (Node inspector)
```

The `Dockerfile` builds in two stages: a `builder` stage installs dependencies and compiles the project, and a `runner` stage copies over just the compiled output, running as a non-root `node` user with a healthcheck against `/`.

The `server` container starts only once Redis and the database report healthy. Each compose file defines a healthcheck for them (`redis-cli ping`, `mongosh` or `pg_isready`) and `server` waits on it with `depends_on`, because the server doesn't retry its first connection and used to exit when a database was still starting.

## Prerequisites

- [Docker](https://www.docker.com/) Engine with the Compose plugin

## Running the Stack

1. Clone the repository.
   ```bash
   git clone https://github.com/rapidrest/auth-server.git
   cd auth-server
   ```
2. Run `docker compose up` using the database specific yaml (`docker-compose.mongo.yml` for Mongo, `docker-compose.sql.yml` for SQL). There is no default `docker-compose.yml`, so `-f` is required and goes before the subcommand.
   ```bash
   # MongoDB
   docker compose -f docker-compose.mongo.yml up --build

   # PostgreSQL
   docker compose -f docker-compose.sql.yml up --build
   ```
3. Open a browser to [http://localhost:3000](http://localhost:3000).

The compose files start the server with `NODE_ENV=dev` (override it by exporting `NODE_ENV`). The secrets below are development defaults, so don't expose this stack publicly as is.

## Configuration and installation details

### Debug and override overlays

Two optional yaml files layer on top of either datastore variant to aid during debugging.

| File | Adds |
|---|---|
| `docker-compose.override.yml` | Publishes the datastore ports (`5432` for Postgres, `6379` for Redis) to the host. Docker Compose reads it automatically only when no `-f` is given, so name it explicitly. |
| `docker-compose.debug.yml` | Runs `yarn debug` instead of the built server and bind-mounts `./src` and `./apps`, so edits on the host take effect without rebuilding the image. Exposes port `9229` for remote debugging. |

For example, a live-reloading SQL setup with datastore ports exposed:

```bash
docker compose -f docker-compose.sql.yml -f docker-compose.override.yml -f docker-compose.debug.yml up
```

### Environment variable overrides

The server [configuration](/docs/core-concepts/configuration) can be overridden in docker by modifying the `environment` section of the yaml file. Nested config variables can be referenced by replacing `:` with double underscore `__` (e.g. `datastores:mongo:url` becomes `datastores__mongo__url`).

For example, overriding the mongo and cache datastores is done as follows:

```bash
services:
  server:
    environment:
      datastores__mongo__url=mongodb://mongo
      datastores__cache__url=redis://redis
```

### Production secrets

`auth-server` ships with fixed development defaults for `cookie_secret`, `auth:secret`, `session:secret` and `auth:oauth_server:keys:encryption_key`. It refuses to start in production (`environment` or `NODE_ENV` set to `production`) if any of the four are still at their default value, and names the ones to set. Before deploying for real, set `COOKIE_SECRET`, `AUTH__SECRET`, `SESSION__SECRET` and `AUTH__OAUTH_SERVER__KEYS__ENCRYPTION_KEY` (64 hex characters) to unique values. Also set `AUTH__TOTP__ENCRYPTION_KEY` (64 hex characters), or every user's TOTP secret is stored in plaintext. The server warns, without refusing to start, if a sign-in provider still has its placeholder credentials. The [Helm chart](/docs/auth/auth-server/deployment/helm#secrets) generates and keeps all of these for you.

Once data has been encrypted, the two encryption keys can't change casually, since anything encrypted with the old key becomes unreadable.
