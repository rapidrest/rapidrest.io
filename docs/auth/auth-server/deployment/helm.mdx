# Kubernetes (Helm)

Running `auth-server` for real, with more than one replica, rolling upgrades, TLS and no single host to babysit by hand, calls for something more than `docker compose up`. The `auth-server` project ships a [Helm](https://helm.sh) chart for exactly that. It deploys the server to a [Kubernetes](https://kubernetes.io/) cluster alongside MongoDB or PostgreSQL and Redis, either bundled or pointed at instances you already run, and exposes it through a Gateway API `Gateway` with TLS. See [Docker Compose](/docs/auth/auth-server/deployment/docker) instead for local development or a small single-host deployment.

A chart is published to [GitHub](https://github.com/orgs/rapidrest/packages) as `oci://ghcr.io/rapidrest/charts/auth-server` for every tagged release, versioned to match the release tag. The current release is `1.0.0`.

## Architecture

The chart deploys `auth-server` as a stateless Kubernetes `Deployment` behind a single `Service`. A Gateway API `Gateway` (created by the chart, Envoy Gateway by default) terminates TLS and an `HTTPRoute` forwards requests to the `Service`. Each pod waits, via init containers, for its bundled datastores to accept connections before starting.

```text
      ----------------------------           ---------------           -----------
     |  Gateway (envoy)           |  --->   |   HTTPRoute   |  --->   |  Service  |
     |  :80 redirect, :443 TLS    |          ---------------           -----------
      ----------------------------                                          |
             ^                                    -----------------------------------------
             |                                   |                    |                    |
       cert-manager                         ------------         ------------         ------------
       (Issuer, Certificate)               |    Pod     |       |    Pod     |  ...  |    Pod     |
                                           | (replica)  |       | (replica)  |       | (replica)  |
                                            ------------         ------------         ------------
                                                  |                    |                    |
                                                  -----------------------------------------
                                                                       |
                                                       -------------------------------
                                                      |                               |
                                                 ------------                    ------------
                                                |  MongoDB   |                  |   Redis    |
                                                |     or     |                  | (optional, |
                                                | PostgreSQL |                  | standalone)|
                                                | (optional, |                   ------------
                                                | standalone)|
                                                 ------------

   Optional: OpenBao  --(External Secrets)-->  Kubernetes Secrets loaded by the pods
```

MongoDB, PostgreSQL and Redis are each optional, standalone Bitnami subcharts, bundled by default (`mongodb.create`, `postgresql.create`, `redis.create`). `auth-server` uses one primary datastore at a time, chosen by `global.database.type` (`mongo` or `sql`). Pointing the chart at datastores you already run is covered under [Datastores](#datastores).

## Prerequisites

- Kubernetes and Helm 3.8.0+
- A Gateway API implementation. The chart defaults to the `envoy` `GatewayClass` provided by [Envoy Gateway](https://gateway.envoyproxy.io); set `global.gateway.className` for another. The chart deploys a `Gateway` and `HTTPRoute`, not an `Ingress`.
- PV provisioner support in the underlying infrastructure, since the bundled MongoDB or PostgreSQL persists data to a PVC by default
- [cert-manager](https://cert-manager.io/), when `global.gateway.tls` is on (the default) and `host` is a public name. TLS is skipped for `localhost`, `*.localhost` and `*.local` hosts.
- [External Secrets](https://external-secrets.io) and [OpenBao](https://openbao.org), only when `global.openbao.enabled` is `true`
- [metrics-server](https://github.com/kubernetes-sigs/metrics-server), optional, for live pod CPU and memory on the admin console's Diagnostics page (k3s ships it)

## Installing the Chart

```bash
helm install --create-namespace --namespace auth-server auth-server \
  oci://ghcr.io/rapidrest/charts/auth-server \
  --version 1.0.0 \
  --set global.domain=example.com
```

The server is then served at `auth.example.com`. Set `host` to use a different name. See [Parameters](#parameters) for every configurable value.

To install from a checkout instead:

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm dep up ./helm
helm install --create-namespace --namespace auth-server auth-server ./helm
```

On a single Linux machine, `scripts/k3s_install.sh` in the repository sets up everything above for you. See [Single-node install with k3s](#single-node-install-with-k3s).

:::note[Secrets and `helm template`]
The chart generates its secrets on first install and reads them back from the cluster on every upgrade. Rendering without cluster access (`helm template`, a GitOps controller such as Argo CD, `--dry-run`) can't read them back, so the render fails and names the values to set. Set them explicitly, use `global.secrets.existingSecret`, or use [OpenBao](#secrets-and-openbao).
:::

## Uninstalling the Chart

```bash
helm uninstall auth-server --namespace auth-server
```

## Configuration and installation details

### Host and domain

`global.domain` is the one value most installs set. `host` defaults to `auth.<global.domain>` and drives the `Gateway` listener hostname, the `HTTPRoute`, the TLS certificate, the allowed CORS origins and the JWT issuer. The JWT audience defaults to the domain. `environment` is `production` and sets both `NODE_ENV` and `environment` on the pod. In production the server refuses to start while any of its development default secrets are in effect, which the chart avoids by generating its own.

### Gateway and TLS

The chart creates a `Gateway` named `<release>-gateway` in the release namespace (`global.gateway.className`, `envoy` by default) with an HTTP listener and, when TLS applies, an HTTPS listener. With `global.gateway.tls` on and a public host, cert-manager issues the certificate through an ACME (Let's Encrypt) `Issuer` the chart creates, using `global.certmanager.email` for the account. Plain HTTP is then redirected (301) to HTTPS. Set `global.gateway.httpRedirect: false` when something in front of the `Gateway` already ends TLS and forwards plain HTTP to it (Cloudflare "flexible" SSL, a load balancer's TLS listener), or every request redirects to itself in a loop.

Every response carries `X-Content-Type-Options`, `Referrer-Policy` and a baseline `Content-Security-Policy`, plus `Strict-Transport-Security` unless `global.gateway.hsts` is `false`.

To share a `Gateway` that already exists, set `global.gateway.name` and `global.gateway.namespace` to it. The chart then creates no `Gateway`, attaches its `HTTPRoute` to yours, and adds a `ReferenceGrant` so that `Gateway` can read the certificate `Secret` in the release namespace. The `Issuer` is likewise only created when `global.certmanager.name` and `namespace` are left at their defaults.

### Secrets

The cookie, session and JWT signing secrets, and the two AES-256 encryption keys (`auth__oauth_server__keys__encryption_key`, which protects the OAuth server's signing keys and stored messaging credentials, and `auth__totp__encryption_key`, which protects every user's TOTP secret), are each generated once on install and kept in the release's Secrets. Upgrades read them back, so sessions stay valid and encrypted data stays readable. Set your own with `global.secrets.cookies`, `global.secrets.sessions`, `global.jwt.secret`, and the two keys under `service.config`. Point `global.secrets.existingSecret` at a Secret you manage to skip generation.

Once data has been encrypted, the two encryption keys can't change casually, because anything encrypted with the old key becomes unreadable.

### Default accounts

`global.defaultAccounts` lists the accounts created on first start. An empty `password` is generated at install, stored in the release's `-service-secrets` Secret and printed in the chart's notes (`helm get notes auth-server -n auth-server`). The default is a single `admin` account with the `admin` role.

### Datastores

`global.database.type` is `mongo` or `sql` and selects which server entry point the pod runs and which subchart settings apply. For PostgreSQL, set `--set global.database.type=sql --set mongodb.create=false --set postgresql.create=true`.

MongoDB keeps application data and ACL data in two databases (`service.datastores.mongodb.mongo.name`, `service.datastores.mongodb.acl.name`). PostgreSQL provisions one database (`postgresql.auth.database`) and, by default, reuses its built-in `postgres` database for ACL data (`service.datastores.postgresql.name`). The bundled MongoDB uses the `Recreate` update strategy because one `mongod` owns the data directory at a time. Redis backs the cache, event bus and log streaming and runs without persistence.

To use datastores you already run, set the matching `create` to `false` and either set `service.datastores.<db>.*.host` or supply full URLs through `global.database.url` (rendered as a template with `mongoProtocol`, `host`, `user` and `password` available) and `global.cache.url`. When `global.cache.enabled` is `false` no cache, events or log datastore is configured.

### Resources and pod security

Neither the server nor the bundled datastores set resource limits, only requests. A limit throttles a pod's CPU or kills it for memory even when the node has room to spare, and MongoDB's liveness probe was timing out at its CPU cap. The Bitnami `resourcesPreset` is therefore `none` for each subchart. The server runs as a non-root user with a restricted profile (`allowPrivilegeEscalation: false`, all capabilities dropped, `RuntimeDefault` seccomp), and a `preStop` sleep plus `terminationGracePeriodSeconds` let it drain behind the `Gateway`.

### Service account and Diagnostics

`global.serviceAccount.create` makes a `ServiceAccount` for the pod. Annotate it through `global.serviceAccount.annotations`, for example with an AWS IRSA role ARN so SES mail and S3 storage get credentials. `global.diagnostics.rbac.create` adds a read-only, namespace-scoped `Role` and `RoleBinding` on that account so the admin console's [Diagnostics](/docs/auth/auth-server/operations#diagnostics) page can read the namespace's pods, volume claims and pod metrics. Turn it off to keep the server from reading the Kubernetes API.

### Passkeys

WebAuthn refuses to work unless the relying party ID and origin match the real domain. The chart sets `auth__passkey__rpID`, `auth__passkey__origin` and the `auth__fido2__*` equivalents to the server's own host and origin. Override any of them under `service.config`.

### Extra configuration

`service.config` merges key/value pairs into the pod's environment, using the same `__` nesting as [Docker](/docs/auth/auth-server/deployment/docker#environment-variable-overrides) (for example `smtp_config__host`). A key set here replaces a value the chart would derive itself. `service.extraEnv` takes full Kubernetes `env` entries, which is the place for secret references such as the SMTP password:

```yaml
service:
  extraEnv:
    - name: smtp_config__auth__pass
      valueFrom: { secretKeyRef: { name: smtp-credentials, key: password } }
```

`service.spec` merges arbitrary fields into the pod spec, for example `nodeSelector` or `tolerations`.

### Secrets and OpenBao

With `global.openbao.enabled`, the JWT, cookie and session secrets and the two encryption keys live in [OpenBao](https://openbao.org), and External Secrets copies them into the Kubernetes Secrets the pod loads. Each value is written once and never rewritten, so upgrades don't invalidate tokens, cookies or sessions.

OpenBao and External Secrets are prerequisites, like cert-manager, and the chart installs neither. The render fails with the install command when the External Secrets CRDs are missing. The vault must hold `auth_secret`, `cookie_secret`, `session__secret`, `oauth_server_encryption_key` and `totp_encryption_key` (the last two as 64-character hex strings) under `global.openbao.kvMount` at `global.openbao.secretsPath` (`<release>/secrets` by default). `global.openbao.auth.method` is `token` (a Secret named by `auth.tokenSecret`) or `kubernetes` (authenticates with a ServiceAccount, requires `auth.kubernetes.role`). If the vault's listener certificate is signed by a private CA, set `global.openbao.caConfigMap` to a ConfigMap in the release namespace that holds the CA under `ca.crt`.

### Single-node install with k3s

`scripts/k3s_install.sh` installs k3s, Envoy Gateway, cert-manager, External Secrets and OpenBao, then the chart. Run it on any Linux machine:

```bash
./scripts/k3s_install.sh --domain example.com
```

Its options include `--domain`, `--auth-host`, `--version` (the chart version), `--tls`, `--email` (for the ACME account), `--openbao true|false`, `--skip-k3s` (use the cluster already there) and `--uninstall`. Run it with `--help` for the full list.
