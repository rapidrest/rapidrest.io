# Data Fetching

A page rendered entirely on the server needs its data before it can render; there's no client-side fetch happening afterward the way a single-page app might do it. `@rapidrest/react` gives you three different places to supply that data, depending on how simple the need is or how deeply it has to reach into RapidREST's own dependency injection, and merges whatever each one returns into the page's props on every request:

```text
props = { userUid, user, params, ...pageProps, ...serviceProps, ...routeProps }
```

Later sources win on overlapping keys. A route-class override can always override a service, which can always override the page itself. `userUid`, `user` and `params` come from the request before any of the sources below run. The three sources run concurrently, so none of them can depend on another's result.

The same merged props are passed to the page component, to `_layout.tsx`, and to `_shell.tsx` when client-side navigation is enabled, so a layout can render page-specific values such as an Open Graph tag without the page doing anything extra.

## Controlling which `user` fields are exposed

`userUid` (just `req.user?.uid`) is always passed to page props when a request is authenticated. The full `user` prop, however, is allow-listed: `ReactRoute` won't expose any `req.user` fields as `props.user` unless you opt in on your route subclass with `userFields`:

```ts
@Route('/app')
export class AppRouter extends ReactRoute {
  protected override readonly userFields: string[] | null = ['uid', 'email'];
}
```

| Property | Type | Default | What it controls |
|---|---|---|---|
| `userFields` | `string[] \| null` | `null` | Names of `req.user` fields to copy onto `props.user`. `null` means no `user` prop is exposed at all — only the scalar `userUid`. |

With `userFields` left at its default `null`, pages and the hydration payload only ever see `userUid`, not the rest of `req.user` — useful when a page just needs to know *who* is logged in without leaking the full user record (roles, hashed credentials, etc.) into client-visible props. Set `userFields` to the specific field names a page actually needs (e.g. `['uid', 'email', 'displayName']`); fields not present on `req.user` are silently skipped rather than showing up as `undefined`.

Because `userFields` is a property on the route class, it applies to every page served by that route — there's no per-page override.

## Page-level `fetchProps`

The simplest option: export an async `fetchProps` function from the page file itself.

```tsx
// app/pets.tsx
import type {HttpRequest} from '@rapidrest/service-core';

export async function fetchProps(req: HttpRequest) {
  return {pets: await fetch('/api/pets').then((r) => r.json())};
}

export default function PetsPage({pets}: {pets: string[]}) {
  return (
    <ul>
      {pets.map((p) => <li key={p}>{p}</li>)}
    </ul>
  );
}
```

This is enough for most pages, and keeps the data-fetching code next to the component that uses it.

## Injecting server-side services with `@ReactService`

For data that needs RapidREST's own dependency injection (a database-backed service, a cache client, anything you'd normally `@Inject` into a route), register a service class against a specific page path with `@ReactService`:

```ts
// src/services/PetService.ts
import {ReactService} from '@rapidrest/react';
import type {HttpRequest} from '@rapidrest/service-core';

@ReactService('/app/pets')
export class PetService {
  async fetchProps(req: HttpRequest) {
    return {pets: await this.petRepo.findAll()};
  }
}
```

The path is the page's public URL, mount prefix included. A route mounted at `/admin` only runs the services whose paths are under `/admin`, and a prefix only counts in whole segments (`/admin` does not cover `/administrators`). `@ReactService` also accepts an array of paths to bind one service to several pages.

Because this is a plain class discovered by [auto-discovery](/docs/core-concepts/auto-discovery), you can `@Inject` a repository, another service, or config into it exactly as you would in a route class. RapidREST instantiates it once, during startup and before the first request is served, and calls its `fetchProps(req)` for every request to the matching path, merging the result in after the page's own `fetchProps`. Trailing slashes, doubled slashes and percent-encoding in the request URL are normalized before the lookup. If two service classes claim the same page, the one listed first by auto-discovery wins.

### Services for dynamic routes

A service path may contain `:name` tokens to bind to a [dynamic page](/docs/ssr-react/app-convention#dynamic-routes):

```ts
@ReactService('/app/pets/:id')
export class PetDetailService {
  @Inject(RepoUtils, {name: Pet.name, args: [Pet]})
  private petRepo?: RepoUtils<Pet>;

  async fetchProps(req: HttpRequest) {
    return {pet: await this.petRepo?.findById(req.params.id)};
  }
}
```

A service belongs to the page whose route its path names, not to every URL that happens to match it. `/app/pets/:id` is `app/pets/[id].tsx`, so a literal `app/pets/featured.tsx` beside it has its own service or none. A token's name does not have to match the bracket's name (`:petId` works for `[id].tsx`), because `req.params` always uses the names from the page file. Where a literal path and a dynamic template both fit, the literal one wins.

A service may also implement `getStaticPaths()` to enumerate its pages for [static export](/docs/ssr-react/static-export#dynamic-routes).

## Overriding at the route-class level

The route class mounting your app (the one extending `ReactRoute`) can also override `fetchProps` directly. This is the last, most authoritative layer, and a good place for cross-cutting data every page needs:

```ts
@Route('/app')
export class AppRouter extends ReactRoute {
  protected override async fetchProps(req: HttpRequest) {
    return {featureFlags: await this.flagsService.getAll()};
  }
}
```

Return `{}` for paths you don't want to affect, so page- and service-level props for those paths pass through untouched.
